4. PRIMARY ARCHITECTURE CONFLICT
=====================================================================
There are two different analysis/metering systems in active code:

A. Canonical plugin path
- Source/DSP/*
- Source/UI/*
- Source/Plugin/*
- Source/Interpretation/*

B. Modular/standalone path
- modules/metering/*
- modules/reference_engine/*
- modules/aifr3d_core/*
- modules/ui/*
- apps/dawai/*

Problem:
- Path A is closer to real engineering measurement.
- Path B still contains approximations, fake reference fallbacks, proxy candles,
  and preset/action behavior.
- This means the repo cannot honestly behave like one coherent instrument.

Required direction:
- Declare one canonical DSP/metering path.
- All products must consume the same analyzer math and the same reference data
  contracts.
- Advisory/chat may interpret measurements, but it must not replace them.

5. MOST IMPORTANT FAILURES: PLUGIN BREAKS / TRUST BREAKS
=====================================================================
These are the highest-priority issues because they break measurement truth,
reference truth, or user trust.

5.1 Mid-only activity detection can hide valid stereo content
Files:
- Source/DSP/FeatureExtractor.cpp
- Source/DSP/AnalysisEngine.cpp
Issue:
- Feature extraction computes RMS/peak from Mid only.
- Analysis activity gating then uses those values to decide if input is active.
Why it happens:
- Side-dominant or anti-phase material can produce low Mid energy while still
  containing real audio.
Impact:
- Valid content can be treated as silence.
- Live analysis, scoring, and UI can freeze or under-report wide stereo material.
Fix:
- Base activity detection on max energy across L, R, Mid, and Side or on channel
  pair energy, not Mid alone.

5.2 Crest factor is mislabeled as dynamic range
Files:
- Source/DSP/AnalysisEngine.cpp
Issue:
- crestFactorDb and dynamicRangeDb are both assigned from the same crest value.
Why it happens:
- The output layer collapses two separate concepts into one number.
Impact:
- Any UI or AI statement about dynamic range is technically wrong.
Fix:
- Split crest factor and dynamic range into separate measurements and labels.

5.3 Live vs reference frequency-balance math is inconsistent
Files:
- Source/DSP/AnalysisEngine.cpp
- Source/DSP/ReferenceModel.cpp
Issue:
- Live frequency-balance normalization and reference frequency-balance
  normalization use different dB-to-linear conversions.
Why it happens:
- One side uses 10^(db/20) and the other side uses 10^(db/10) for conceptually
  related feature normalization.
Impact:
- Reference comparisons can drift even when live and reference tonal balance are
  actually similar.
Fix:
- Standardize one domain for band-energy comparison and keep it consistent in
  live, stored reference, and scoring paths.

5.4 Standalone UI fabricates fallback reference data
Files:
- modules/ui/src/main_view.cpp
Issue:
- When reference lookup fails, the code creates a fake reference from the live
  snapshot with arbitrary offsets.
Why it happens:
- The standalone path tries to keep the interface populated even without a real
  pool match.
Impact:
- The user is shown a false target.
- Meter color states and scoring become invented.
- This directly violates the requirement that measured metrics remain true.
Fix:
- Remove fake fallback reference creation.
- If no valid reference exists, show live-only meters with neutral evaluation
  state and explicit "reference unavailable" messaging.

5.5 Standalone session candles are not real loudness candles
Files:
- modules/ui/src/main_view.cpp
Issue:
- Session candles are generated from alignment/signature proxy values instead of
  real LUFS open/high/low/close.
Why it happens:
- The candle engine was built around score-like proxies, not engineering units.
Impact:
- Candle charts look active but do not reflect actual loudness history.
Fix:
- Store real LUFS-based OHLC values for realtime and session candles.

5.6 Modular loudness path is explicitly approximate
Files:
- modules/metering/src/loudness_analyzer.cpp
Issue:
- Loudness conversion is approximate, not standards-grade BS.1770 behavior.
Why it happens:
- The path uses simplified energy conversion without full K-weighting/gating.
Impact:
- It cannot match Youlean-level measurement agreement.
Fix:
- Replace with a proper BS.1770-4 implementation or reuse the canonical
  loudness engine everywhere.

5.7 Modular true peak is fake
Files:
- modules/metering/src/loudness_analyzer.cpp
Issue:
- "True peak" is estimated from adjacent samples instead of oversampling.
Why it happens:
- The implementation does not perform inter-sample peak detection.
Impact:
- Inter-sample peaks are missed.
- True peak readouts are not trustworthy.
Fix:
- Implement calibrated oversampling, minimum 4x, with max abs across the
  oversampled waveform.

5.8 Modular FFT analyzer is not production-grade
Files:
- modules/metering/src/fft_analyzer.cpp
Issue:
- Uses a naive O(N^2) DFT on the current block only.
Why it happens:
- No rolling analysis buffer, no proper FFT engine, no overlap handling.
Impact:
- jumpy spectrum
- poor low-end stability
- poor realtime performance
Fix:
- Replace with a proper FFT path, rolling window, overlap, Hann window, and
  power-domain smoothing.

5.9 Modular stereo width math is wrong for the target contract
Files:
- modules/metering/src/stereo_analyzer.cpp
Issue:
- Width is computed as sideEnergy / (midEnergy + epsilon) and clamped 0..2.
Why it happens:
- The path uses a ratio that can exceed normalized bounds.
Impact:
- Width values do not match the required 0..1 contract.
Fix:
- Use sideEnergy / (midEnergy + sideEnergy) in the canonical path.

5.10 Server/admin chat path is not grounded in live DSP by default
Files:
- server/src/index.js
Issue:
- /api/v1/chat/ask uses prompt plus memory summary, but not a live analysis
  payload from the mix engine by default.
Why it happens:
- The remote chat route is structured like a generic assistant endpoint.
Impact:
- Admin/web chat can produce valid structured responses that are not actually
  tied to live meter truth.
Fix:
- Add mandatory analysis payload ingestion for mix-analysis requests or separate
  generic admin chat from mix-grounded advisory.

5.11 Preset/action logic exists and can manipulate session state
Files:
- modules/aifr3d_core/src/apply_fix.cpp
- modules/ui/src/main_view.cpp
- tests/apply_fix_undo_test.cpp
Issue:
- The repo still contains preset-generation and action/undo logic.
- The standalone UI can apply a conservative level move and preview by soloing a
  track.
Why it happens:
- AIFR3D core still includes a "fix apply" concept.
Impact:
- This conflicts directly with the stated requirement that AIFR3D must not
  generate presets or manipulate the host/session as part of advisory behavior.
Fix:
- Remove AI-driven action generation and session-manipulation pathways from the
  product contract.
- If any manual tooling remains, it must be explicit, separate, and not driven by
  chat output.

7. UI / METER BEHAVIOR AUDIT
=====================================================================
7.1 Meters are too jumpy because the repo mixes bad analysis cadence and generic smoothing
Relevant files:
- Source/UI/UiModel.cpp
- modules/ui/src/main_view.cpp
- modules/ui/src/meter_panel.cpp

Findings:
- Generic SmoothedValue ramps are used where instrument ballistics should exist.
- The standalone path only runs higher-level analysis every few UI ticks.
- The modular FFT sees only the current block.
- Proxy-based candles and score-based motion amplify instability.

Why the meters "jump all over the place":
- The underlying measurement path is unstable in the modular stack.
- The smoothing strategy is not meter-specific.
- Some UI animation layers are ornamental rather than strictly informative.

Required meter-ballistics model:
- Sample peak / true peak:
  - instant attack
  - hold peak briefly
  - fixed dB-per-second release
- Momentary LUFS:
  - let the 400 ms window do most of the smoothing
  - only light display smoothing if needed
- Short-term LUFS:
  - almost no added display smoothing
- Integrated LUFS:
  - no cosmetic smoothing beyond the real computation
- Correlation / width / phase:
  - 150-300 ms EMA or equivalent
- Spectrum:
  - overlap FFT
  - power-domain smoothing
  - optional peak-hold overlay instead of hiding movement

7.2 Candles must be rebuilt in real units
Plugin path files:
- Source/UI/UiModel.cpp
- Source/UI/CandleStoryline.cpp
Standalone path files:
- modules/ui/src/main_view.cpp

Required fix:
- Realtime candle mode = actual loudness window OHLC
- Session candle mode = actual session start/end integrated LUFS plus short-term
  high/low behavior
- No score-derived candle body values

7.3 Color logic needs separation by mode

Required separation:
